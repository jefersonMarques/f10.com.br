# Ticket number continuity and legacy lookup

## Current state

- `tickets.id` is the stable UUID used by internal routes and ticket relationships.
- `tickets.ticket_number` is the current unique sequential number.
- `movidesk_ticket_imports.source_ticket_id` preserves the original Movidesk number.
- The ticket workspace can search for the current number and the Movidesk number, including closed tickets.
- Ticket numbers already sent by email must not become untraceable after renumbering.

## Read-only number audit

```bash
cd /opt/f10.com.br
node --env-file-if-exists=.env --env-file-if-exists=.env.production \
  scripts/audit-ticket-number-reconciliation.mjs
```

The report includes the maximum Movidesk number, current collisions, native F10 tickets in the legacy range, and an estimated safe start for new numbers. It does not change records or sequences.

## Guarded one-time renumbering

The audit found 31,120 imported tickets, 109 native F10 tickets, and a maximum
Movidesk source number of 43,212. These counts must be confirmed again by the
migration preview. The 31,085-row final snapshot is not the whole import
inventory: other Movidesk tickets were also imported.

The application migration `0120_ticket_number_continuity.sql` creates a
persistent alias table and a one-time execution record. Deploy and apply
database migrations before running the renumbering script.

1. Make a tested, restorable PostgreSQL backup and arrange a maintenance window.
   The migration briefly locks `tickets` against concurrent reads and writes.
2. Preview the current database state (read only):

```bash
cd /opt/f10.com.br
node --env-file-if-exists=.env --env-file-if-exists=.env.production \
  scripts/reconcile-ticket-numbers.mjs
```

3. Verify `ticketCount`, `numbersToChange`, `nativeStartingNumber`,
   `collidingPreviousNumbers` and the 64-character `planHash`. The script
   reevaluates all numbers when applying. Any change to a ticket before
   application invalidates the hash and blocks the operation.
4. Only after reviewing the preview, apply it using the exact reported hash:

```bash
node --env-file-if-exists=.env --env-file-if-exists=.env.production \
  scripts/reconcile-ticket-numbers.mjs \
  --apply --expect-hash <64-character-planHash>
```

The database transaction inserts aliases before updating any ticket number.
Because ticket numbers are `GENERATED ALWAYS AS IDENTITY`, it temporarily
switches this column to `GENERATED BY DEFAULT`, applies the numbers, and
restores `GENERATED ALWAYS` before committing. Any failure rolls back the
column-definition change along with the ticket updates. A temporary set of
numbers prevents unique-key conflicts, followed by the final original
Movidesk numbers and consecutive native ticket numbers.
The UUID and all related rows remain unchanged. The database sequence is
advanced beyond the highest assigned number. Any SQL error rolls back the
ticket and alias changes. Sequence values themselves are not transactional.

A completed migration is recorded in
`ticket_number_reconciliation_runs` and cannot be run again. New native tickets
continue from the next available sequence number. Never delete the
`ticket_number_aliases` records: they preserve the previous F10 numbers,
including previous numbers of imported tickets that may have appeared in emails.

## Lookup and ambiguity

- Operators can search for a current ticket number, an original Movidesk
  number, or a previous F10 number.
- An alias result displays `Anterior #…` beside the current ticket number.
- A numeric query may match several different tickets (for example, a new
  Movidesk number and a previous F10 number). All authorized matches are
  listed; the search must never silently redirect by number.
- Customers can search previous F10 numbers in their portal, but only among
  tickets they already have permission to view. The migration does **not**
  grant access to historical Movidesk content or alter ownership.
- Existing links based on ticket UUIDs remain valid. Integrations that store
  only bare numbers must handle ambiguity explicitly.


## Historical action anomalies

The final reconciliation reported 40 failed tickets plus one from an earlier batch. Snapshot inspection found 45 tickets with duplicate action IDs; 20 have conflicting internal/public action types and 25 have the same type but different content. **Do not collapse or automatically overwrite these actions.** Audit the imported message mapping and retain both variants with distinct provenance before any repair. Four duplicate-action tickets completed without errors and still require a content-integrity review.
